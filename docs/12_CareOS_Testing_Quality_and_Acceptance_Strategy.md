# CareOS — Testing, Quality & Acceptance Strategy

**Client:** American Care Team (Maryland) · **Document:** 12 of 15 · **Version:** 1.1 (Draft) · **Prepared by:** OCTSERVICES LLC
**Implements:** verification for Docs 01–11 and Doc 17 §12; acceptance mechanics for Doc 04 milestones; release gates referenced by Doc 13 CI.

> **Change note (v1.1, Aug 10 2026):** §2 gains a status column, so the document stops implying coverage the repository does not yet run; the E2E-mobile row is withdrawn under **D-022**. §3.1 records the ten pgTAP files added with the Verified Visit & Workforce Intelligence layer and the suite's current size (40 files, 1,718 assertions). §4.1 specifies the seven verified-visit journeys **as a contract, not a report** — none has been executed. §6 adds the coordinate canary obligation under **D-030** and names which assertions already enforce it and which do not. §5, §7, §9 and §10 updated to match. The operative new rule: a suite counts as coverage only once it has run green in CI.

> **Purpose.** In a compliance product, tests are not engineering hygiene — they are the *evidence* that the guarantees we sell (nothing lost, least privilege, cadences enforced, AI governed) are true, continuously. This document defines what is tested, how, with what data, and what "done" and "accepted" mean.

---

## 1. Quality philosophy

1. **The guarantees get the strongest tests.** Append-only, RLS, audit chain, cadence math, EVV integrity, and AI tier-gating are tested *in the database*, where they're enforced — not just through the UI.
2. **Traceability is a deliverable.** Every FR/NFR maps to named tests; the matrix is generated, versioned, and shown at acceptance. "Prove it" is answerable for requirements, not just records.
3. **Synthetic data only outside production.** No exceptions, ever (D-006). A seeded persona universe ("Meadowbrook" dataset: 25 clients, 40 staff, 90 days of visits, deliberate edge cases) powers every environment and demo.
4. **Test the failure modes on purpose.** Offline, conflict, ISAS-down, AI-down, low-confidence, injection — the degraded paths are release-gated, because that's where trust is won or lost.

## 3. The pgTAP compliance suite (what makes this product defensible)

Run on every PR against a from-scratch migrated database. **Current size: 40 files, 1,718 assertions** — the whole suite green is the precondition for every other claim in this document. Files are named for the migration they prove (`supabase/tests/database/00NN_*.sql`), each opens with a header stating what it is claiming and a `@trace` line binding it to its story and decisions, and each declares `no_plan()` so an added assertion never has to fight a plan count.

- **RLS matrix.** Generated tests over (role × representative-row × operation): for each table, fixtures create rows owned by tenant-A/tenant-B, on-team/off-team, AAL1/AAL2 sessions; assertions enumerate expected allow/deny. Adding a table without matrix coverage **fails the build** (`matrix.yaml` + `scripts/check-matrix.sh`, wired as its own CI job). ~700 assertions at v1; ~1,718 after the verified-visit layer.
- **Append-only.** For every [AO] table: `UPDATE`/`DELETE` as every role (incl. a simulated table-owner path) raises `CAREOS_APPEND_ONLY`; privilege probes confirm grants absent.
- **Audit chain.** Insert sequence → recompute hashes → assert linkage; simulated tamper (superuser row edit in test) breaks verification; anchor job output matches recomputation.
- **RPC guards.** `finalize_form` without signatures/AAL2/permission fails with exact codes; `clock_in` idempotency (same `client_event_id` twice → one event); geofence in/out cases (PostGIS fixtures); `assert_schedulable` blocks lapsed-credential assignment.
- **Cadence engine.** Time-travel fixtures (`clock` injection): admission → initial/48-h/annual obligations at correct dates; medication-involvement 45/90/120 supervisory cadence; grace transitions `open→at_risk→overdue`; waiver path requires RN role + reason; leap-year/DST edges.
- **AI invariants.** Tier-gating (T1 cannot reach `executed` without approval row), capability-flag kill switch honored, budget hard-stop.

| `0045_verified_visit.sql` | The four orthogonal state axes exist and are RPC-only (the column-level `UPDATE` tightening on `public.visit` is asserted, not assumed); the clock ledger accepts its new event types and its idempotency key exactly once; `visit_event` stays append-only at both layers; `public.verified_visit` derives minutes from the ledger under the caller's own RLS; no coordinate reaches the view or the audit ledger |

## 4. E2E critical journeys (release-gated)

> **Status: specified, not proven.** None of the journeys in this section has been executed end to end. They were authored alongside the verified-visit layer but shipped in no verified-visit commit, they are not a CI stage, and no environment has yet run them against a live Supabase Auth + PostgREST stack. Everything here is therefore a **contract** — the definition of what passing means — not a description of coverage that exists. Until a run is green in CI, no release gate (§9) may be marked on the strength of an E2E journey, and acceptance evidence for these flows is manual and must say so.

Web: intake-from-document (upload→extract→review→client created with provenance) · assessment→AI care-plan draft→RN edit→sign→finalize→locked→correction path · schedule→credential-block→resolve→assign · open-shift fill with agent (approve plan→SMS mock→accept→confirmed) · survey-packet export · access-revocation drill (user separated → all surfaces dead ≤15 min; PowerSync eviction is out of scope while D-022 stands).
Accessibility: axe-clean on gated flows + manual screen-reader pass on caregiver loop and approvals inbox each release (Doc 10 §7).

### 4.1 The verified-visit journeys (Doc 17 §12)

Seven journeys, each ending in a **database assertion** rather than a screenshot — the record is the deliverable, so "the button worked" is not the pass condition. They run against the Meadowbrook universe (§7), on a mid-tier Android viewport for the caregiver flows, and each screen they touch must also be exercised in all four states (Doc 10 §8).

| # | Journey | Passes when |
|---|---|---|
| J1 | **In-fence clock-in.** Caregiver opens `/today`, taps `Clock in` with a position inside the bound geofence | One `visit_event` of type `clock_in` with `location_status='verified'`; `visit.status='in_progress'`; `verification_status='pending'`; the card reads `Clocked in · h:mm` with no metre value anywhere in the DOM |
| J2 | **Out-of-fence → reason → exception.** Same tap with a position outside the fence, under a policy that allows exceptions | First tap appends `clock_in_rejected` and the UI shows `Try again` / `Request exception` with the distance rendered **as words**; submitting a `reason_code` appends the `clock_in`, raises the matching `visit_exception`, and lands the visit in `verification_status='exception'` — care is never blocked, and no exception is raised for a bare retry |
| J3 | **Missing clock-out.** A visit passes `policy.missing_clock_out_minutes` with an open clock-in; `app.sweep_visit_exceptions` runs twice | Exactly one `missing_clock_out` exception exists after the second sweep (idempotence at the surface, not just in SQL); the caregiver sees the prompt; the coordinator sees the row at the top of `/operations/exceptions` |
| J4 | **Correction.** A supervisor with `visit.correct` corrects a clock time with a reason | A `correction` event with `corrects_event_id` set, the original untouched, a `manual_correction` exception raised for review, and the audit event carrying old→new **timestamps** and nothing else |
| J5 | **Approval.** A visit with an open `critical` exception is refused (`CAREOS_APPROVAL_BLOCKED`); the same visit approves once the exception is disposed; the caregiver cannot approve their own hours | One `approved_work_segment`; `approval_status='approved'`; the self-approval attempt refused at the RPC, not merely hidden in the UI |
| J6 | **Period close and export.** A period with an unapproved completed visit refuses to close and **says how many**; after approval it closes and exports | `payroll_period.status='exported'`, one `payroll_export` row with a stable `content_sha256`, and a CSV naming no client |
| J7 | **PWA offline (replaces the airplane-mode device-farm suite, D-022).** Service worker registered; network disabled; a full visit clocked in and out offline; reconnect | The indicator reads `Offline`, then `Syncing (n)` naming the exact count, then `Live`; both events land exactly once (`client_event_id` replay returns the original decision, never a duplicate); a *refused* replay is surfaced to the caregiver rather than swallowed; the IndexedDB queue contains no client name, address or free text at any point; the worker cache contains no navigation response |

**Journey-adjacent invariants worth their own assertions:** the reason picker is unreachable when `visit_policy.allow_location_exception` is false (the hard `CAREOS_GEOFENCE_UNVERIFIED` path); the queue holds one pending intent per (visit, event) so a double tap does not produce two entries; and no caregiver-visible string on any of these screens contains *EVV*, *GPS*, *geofence*, *radius*, *accuracy* or a distance in metres — a lint-style DOM assertion, run on every journey, because Doc 10 §6 makes the vocabulary a contract rather than a preference.

## 5. Integration testing posture

Sandbox-mode connections in staging for Twilio/Checkr/DocuSign/QBO; ISAS per state-provided test modality (Discovery D-Q16) with recorded-fixture contract tests as the fallback harness; chaos drills quarterly: ISAS-down (queue drains, aging alerts fire), model-provider-down (degradation matrix behaviors, Doc 11 §10), Supabase restore drill (Doc 13 §8).

**EVV is testable without the state (D-026).** The canonical `evv_record` carries the six federally required elements and is state-agnostic; adapters translate. Maryland ships as `('isas','MD', mode='reconcile', enabled=false)`, so the layer's correctness is provable today without a live endpoint, and 0049's pgTAP asserts the property that makes that safe: **a disabled adapter is a no-op, not an error** — `app.submit_evv` returns cleanly and enqueues nothing. What still cannot be tested is the wire format, which is what V17/D-Q16 unblock; when they resolve, the change under test is one adapter row and one adapter implementation, not the record model.

## 6. PHI-safety verification (continuous)

**Planted-canary suite:** distinctive fake-PHI markers seeded through fixtures; automated assertions that markers never appear in: log drains, Sentry events, email bodies, notification payloads, AI request bodies outside allowlists, error responses. Runs nightly against staging + on every release. Any hit = SEV-2.

**Coordinates are canary material (D-030).** A caregiver's position at a visit reveals the client's home address, so it is PHI about the *client* and workforce PII about the *caregiver* at the same time. The capture points are closed — clock-in and clock-out only, no continuous tracking, no background location, no mid-visit polling — and a coordinate may exist in exactly two places: the RLS-gated ledger row that captured it (`visit_event.latitude/longitude`) and the human-attested pin it is measured against (`service_location_version.geo`). It must appear in **none** of: `audit.audit_event.payload`, `public.domain_event.payload` (the outbox), notification payloads, queue messages, exception `evidence` objects, observability breakdowns, or any AI prompt. A raw distance in metres and a raw accuracy radius are treated the same way at the caregiver boundary: the field UI receives a `distance_bucket`, never a number (Doc 10 §6).

**This is already enforced at the database layer, and the assertions are not vacuous.** The verified-visit pgTAP files plant a distinctive coordinate and then grep every downstream ledger for it:

- `0046_clock_engine.sql` clocks a visit at a canary latitude (`39.2903117`), **first asserts the value really is in `visit_event`** so the canary cannot pass by accident, then asserts zero occurrences of the full-precision value, of any truncated precision of it, and of the longitude, in both `audit.audit_event.payload` and `public.domain_event.payload` — plus zero occurrences of a coordinate-derived distance in the outbox, and zero occurrences of the caregiver's free-text note in either ledger.
- `0043_geo_service_location.sql` runs the same canary over the attestation path: the verified latitude and longitude, and the address components and label, appear in no audit payload and no outbox payload; an out-of-range coordinate is refused with `CAREOS_BAD_COORDINATES` **and never echoed back in the error**.
- `0047`, `0049`, `0050` and `0051` each carry the same closing canary for the ledgers they add — exception evidence, EVV submissions and queue messages, payroll audit payloads and rejection reasons, and both analytics views (which additionally must not leak a raw accuracy radius).

The obligation that remains **unmet** is the egress half: nothing yet asserts that a coordinate cannot reach a log drain, a Sentry event or an AI request body, because the nightly canary harness described above is not built. The database half is done and is the stronger half — content that never leaves a row cannot leak — but the two are not the same claim and this document does not conflate them.

## 7. Test data management

The Meadowbrook synthetic universe is generated by seed scripts (deterministic, versioned) — realistic names/addresses flagged synthetic, edge personas built-in (client with 4 caregivers, caregiver with expiring license mid-sprint, high-acuity 48-h case, Spanish-speaking family, out-of-fence rural client). Prod-to-staging data flow: **prohibited**; schema-only migrations rehearse on Meadowbrook. AI golden sets are synthetic-PHI documents (generated + hand-corrupted scans for realism).

**Seeds ask the engine; they never re-implement it.** `supabase/seeds/zz_verified_visit.sql` builds the verified-visit slice of Meadowbrook — jittered coordinates over a Montgomery County town centre, hung off names that already exist in the universe — and every derived value in it is produced by the shipped function that owns it: `normalized_address` by `app.normalize_address`, `geo` by `app.geo_point`, distances by `app.distance_m`, `location_status` by `app.evaluate_location`, thresholds by `app.resolve_visit_policy`, the EVV hash by the 0049 canonical form byte for byte, and minutes read off the clock ledger. Nothing is hand-asserted that the product can derive, so fixtures cannot drift from the rules they illustrate. The property that keeps them honest is testable and should be re-checked whenever those rows change: **`select app.sweep_visit_exceptions(now())` against a freshly seeded database returns a total of zero** — the seeded universe is one the real detector has nothing to add to. The seeds are idempotent by construction (id-pinned, `on conflict do nothing`) and are verified by running them twice.

Note the seeding gap the migration chain leaves and the seeds close: 0043–0052 invoke their bootstrap functions with `select app.seed_*(t.id) from public.tenant t`, which covers a hosted tenant that already exists but not local or preview, where the Meadowbrook tenant is created *after* migrations run. Without the seed file those environments have no policy floor (every clock-in fails `CAREOS_POLICY_MISSING`), no EVV adapter, no capability registry and no feature flags.

## 8. Acceptance & UAT (how the client signs off)

Per Doc 04 milestones, each acceptance tranche gets: (1) the **traceability matrix** slice (FR → tests → pass evidence) auto-generated from CI; (2) scripted UAT sessions with real staff on Meadowbrook (coordinator, RN, caregiver, founder tracks — 60–90 min each) with structured findings capture (blocker/major/minor); (3) exit criteria: zero blockers, majors triaged with dates, all release gates green. Founder demo cadence (Doc 15 §7) keeps acceptance continuous rather than big-bang.

## 9. Release gates (the checklist that ships a build)

CI green (all layers incl. pgTAP + AI evals + canary suite) · E2E critical journeys pass on staging · a11y scan clean on gated flows · performance budgets met (Lighthouse-CI + k6 smoke) · no open crit/high security findings · migration rehearsed with rollback note · Security-Advisor findings zero · CHANGELOG + runbook deltas written · feature flags default-safe. **A red gate has no override path except a logged decision by the engagement lead — and that logs to the decision record.**

**What is actually enforced today**, so that "gates green" never means "gates absent": three CI jobs run on every pull request — the full pgTAP suite against a from-scratch migrated database, the spec-corpus drift gate (D-010/ST-103), and the pgTAP matrix-coverage check (ST-110). Type-checking runs locally via `pnpm typecheck`. Every remaining gate in the list above is **unavailable rather than passing**, either because its tooling is not provisioned or because its suite has been authored but never executed (§2, §4). That distinction must appear on the acceptance evidence: an unrun gate reported as green is precisely the failure mode this document exists to prevent.

## 10. Quality metrics (tracked on the exec dashboard, internal)

Escaped-defect rate (prod bugs per release) · flake rate <2% (quarantine-and-fix policy) · **pgTAP assertion count trend (must grow with schema — 1,718 across 40 files at the close of the verified-visit layer)** · E2E runtime <20 min (parallelized) · time-to-green on main · UAT blocker trend across tranches · canary-suite hit count (target: forever zero).
